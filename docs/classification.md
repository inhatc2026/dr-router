# 진료과 분류와 근거 문서 연결

담당: 박태준. 모델 기본값은 `gpt-4.1-mini`이며 `LLM_MODEL`로 변경한다. 2026-11-23 팀 실측과 사용자 승인으로 가이드의 `gpt-4o-mini`에서 변경했다.

최건 님의 동일 프롬프트·RAG 문서 비교(14문항, 제한 30초, 모델별 1회)에서 gpt-4.1-mini는 Top-3 14/14, 중앙값 1.4초·최대 2.4초였다. 이는 작은 표본의 팀 측정이며 실제 운영의 시간 초과 방지나 정확도를 보장하지 않는다. 기존 gpt-4o-mini의 4초 제한 분류 평가는 12/14(실패 2건 모두 시간 초과)였고, 비교 실험은 별도 조건이다. 서버 첫 요청 10.8초도 보고되어 전체 요청이 항상 5초 이내라는 결론은 내리지 않는다.

## 선행 조건

실제 검색에는 RAG PR #13의 `retrieve(query, k=3)` 구현과 각 PC의 벡터 인덱스가 필요하다. 이 분류 변경에는 다른 담당자의 RAG 코드·문서를 복사하지 않았다. #13 병합 전 main의 retriever는 빈 리스트를 반환하는 스텁이므로 상담 안내만 나온다.

프로젝트 루트에서 가상환경을 활성화한 뒤 실행한다.

```powershell
pip install -r requirements.txt
# .env에 LLM_API_KEY를 직접 입력한다. 실제 키는 커밋하지 않는다.
# LLM_MODEL=gpt-4.1-mini (생략 가능; 기존 .env에 모델이 지정되어 있으면 직접 변경)
python -m backend.rag.build_index
python -m uvicorn backend.main:app --reload --port 8001
```

인덱스 생성은 #13이 반영된 코드에서 실행해야 한다. 첫 임베딩 모델 다운로드에는 인터넷과 시간이 필요하다. 병원 검색 DB는 별개이며 #12 병합 후 `python -m backend.tools.hospital_db`로 형식 4에 맞춰 다시 만든다. 인덱스·DB 생성은 이번 분류 검증에서 실행하지 않았다.

## 분류 동작

1. collect가 정리한 증상을 우선 사용한다. 없으면 최근 사용자 발화와 이번 입력을 합친다. 모델에 보낼 데이터에는 위치·전체 State·assistant 발화를 넣지 않는다.
2. 문서 3개를 검색하고 지원 진료과·본문·문서명을 확인한다. 지원 목록은 의과 18개 + 치과, 내과의 세부 분과 3개로 총 22개 분류 이름이다. 세부 분과의 병원 검색은 기존 백엔드에서 내과로 처리한다.
3. 증상과 문서는 system 지시와 분리된 JSON 데이터로 전달한다. LLM은 진단·처방 대신 문서에 근거한 최대 3개 후보와 이유를 생성한다.
4. 문서가 없는 진료과, 범위를 벗어나거나 유한하지 않은 점수, 빈 이유는 제외한다. 중복 과는 최고 점수 하나만 남기고 내림차순 Top-3를 반환한다.
5. 출처는 LLM 출력에서 받지 않고 해당 진료과의 검색 문서명으로 서버가 붙인다. **문서 연결을 검증하는 것이며 reason의 의미적 정확성을 자동 증명하는 것은 아니다.**
6. 키 없음, 검색 결과 없음, 검색/모델 오류, 모델 거절·출력 형식 오류, 1순위 점수 0.5 미만이면 `departments=[]`로 반환하고 기존 방문 상담 안내를 사용한다. 응급 입력은 그래프에서 분류를 건너뛴다.

검색의 코사인 유사도는 분류 점수나 진단 확률이 아니다. LLM의 score도 진단 확률로 표시하지 않는다. 0.5는 FR-14에서 정한 분기 기준이며 의료적 성능 검증 결과가 아니다.

LLM 호출은 SDK timeout 4초, 자동 재시도 0회다. 이는 전체 응답의 4초/5초 상한이 아니다. RAG 초기화·검색·의료기관 조회 시간은 별도이므로 실제 모델로 NFR-07을 다시 측정해야 한다. 키나 모델 설정을 바꾸면 서버를 다시 시작한다.

## 공유 계약 추가: 팀 공지 필요

사용자 승인에 따라 `Department` 및 `DepartmentOut`에 선택 필드 `sources: list[str]`를 추가했다. 기존 `name`, `score`, `reason`은 유지한다. 이전 생산자는 생략할 수 있고 API 기본값은 빈 배열이다.

```json
{
  "name": "정형외과",
  "score": 0.8,
  "reason": "입력 증상과 문서의 진료 범위를 비교한 설명",
  "sources": ["정형외과.md"]
}
```

프론트는 문서명을 안전한 텍스트로 표시한다. 구버전 응답에 출처가 없으면 기존 ‘확인 필요’와 방문 상담 안내를 유지한다. 출처가 있어도 낮은 확신 안내는 유지하며, 출처·reason은 sessionStorage에 보관하지 않는다.

`graph.respond_node()`의 문구만 출처 유무에 맞춰 조정했다. 분류 결과에 근거가 있어도 ‘근거 확인이 필요’라고 나가던 모순을 없앴고, 그래프의 노드·분기·응급 대기 예산은 바꾸지 않았다.

## 평가 및 검증

```powershell
python -X utf8 -m unittest eval.test_classify -v
python -X utf8 -m unittest discover -s eval -t .
npm run test:frontend
$env:PLAYWRIGHT_CHANNEL='msedge'
npm run test:browser
```

실제 LLM 평가는 키와 인덱스를 준비한 뒤 실행한다. 유료 모델 호출이 발생한다.

```powershell
python -X utf8 -m eval.evaluate --mode classify
python -X utf8 -m eval.evaluate --mode pipeline
```

- `classify`는 분류만 평가한다. 기본값이다. 응급 키워드에 걸리는 평가 문장이 분류 품질과 관계없이 오답 처리되던 문제를 분리한다.
- `pipeline`은 기존처럼 응급 분기를 포함한다. 응급 분기로 진료과가 비는 문항도 오답에 포함하며, 순수 분류 정확도와 구분해 출력한다.
- 기존 14문항은 변경하지 않았다. 최소 20문항 요구를 충족하지 않으며 실제 모델 정확도·성능 합격을 선언할 수 없다.
- 로컬 검증은 모델 응답·검색을 모의한다. SDK 직렬화는 HTTP MockTransport로, API 필드 전달은 실제 LangGraph/FastAPI로 확인한다. 실제 외부 LLM 호출은 하지 않는다.

## #12·#13 연결 검토에서 남은 사항

- #12의 전문의 우선 결과를 프론트가 다시 전체 거리순으로 정렬한다. 검색 대상 선정 효과는 남지만 화면 순위는 달라질 수 있다. 기존 FR-20 전체 거리순 합의와 함께 팀 결정이 필요하다. 이번 분류 변경에서 정렬을 바꾸지 않았다.
- #12의 `eval.check_live` 병원 시나리오는 분류 함수를 고정 결과로 대체한다. 분류 구현 후에도 해당 시간 측정만으로 실제 LLM을 포함한 NFR-07 충족을 주장할 수 없다.
- #13의 `1 - cosine_distance`는 음수가 될 수 있어 문서의 ‘0~1’ 설명과 다르다. distance=1.2일 때 score=-0.2를 재현했다. 이번 분류는 검색 score를 LLM 적합도로 사용하지 않는다.
- #13 문서의 공공 의료 원문 출처 확정·검수(IF-07)는 별도다. `정형외과.md` 같은 파일명 표시만으로 원문 출처 검수가 완료되는 것은 아니다.
- #11 리뷰의 카카오맵 길찾기 추가 제안은 별도 후속 작업이다.
